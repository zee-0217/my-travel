# 대화형 일정 수정

AI 일정 생성 후 **대화로 여행 다듬기**에서 자연어로 변경을 요청합니다. 예: “둘째 날 오후의 바다 산책을 실내 전시로 바꾸고, 나머지는 유지해 줘.” 날짜를 명시적으로 제한하려면 수정 범위에서 해당 날짜를 선택합니다. 자동 선택이면 모델이 요청에 필요한 날짜만 선택합니다.

## 기존 Agent Loop 재사용

`createAgentPlanner()`를 생성과 수정에 함께 사용합니다. 별도 도구 실행 파이프라인은 만들지 않습니다.

1. 서버가 현재 일정·원본 구조화 초안·실제 도구 결과를 보관합니다.
2. 수정 요청 때 현재 일정과 새 요청, 기존 검색·경로·날씨 근거를 Responses API에 전달합니다. 전체 채팅 로그나 비밀 키는 전달하지 않습니다.
3. 모델은 기존 callId를 재사용하거나 search_places / get_routes / calculate_budget / get_weather / web_search 중 필요한 것만 선택합니다.
4. 모델이 수정할 날짜의 패치만 반환합니다. 서버가 생략된 날짜의 일정을 유지하며 명시적 수정 범위 밖 패치는 거절합니다. 같은 날짜의 다른 장소도 가능하면 유지하도록 지시합니다.
5. 병합 후 기존 JavaScript 검증·제한된 자동 재계획을 다시 실행합니다. 결과에 변경 이유와 실제 변경 비교를 추가합니다.

기존 검색 결과가 재사용되면 이번 Agent Trace에 새 검색 호출을 만들지 않습니다. Trace는 이번 수정 요청에서 실제 실행된 도구만 표시합니다. 기존 출처와 좌표·경로는 근거가 일치할 때 계속 표시합니다. 지도도 수정한 날짜를 선택해 갱신합니다.

## API

`POST /api/plan` 성공 응답의 `plan`에 불투명한 `planId`를 추가합니다. 수정은 다음과 같습니다.

```http
POST /api/plan/revise
Content-Type: application/json

{
  "planId": "생성 응답에서 받은 ID",
  "request": "둘째 날의 방문 시간을 오후 2시로 바꿔 줘",
  "targetDay": 1
}
```

request는 공백 제외 1~1000자, targetDay는 0부터 시작하는 날짜 번호 또는 null(자동 선택)입니다. 성공 응답은 `200 {plan: ...}`이며 새로운 planId를 발급합니다. 브라우저가 보낸 임의의 currentPlan·가격·좌표·영업시간은 사용하지 않고, ID로 찾은 서버의 일정을 수정합니다.

`plan.edit`에는 request, reason, changes, changedDays, unchangedDays가 있습니다. changes는 서버에서 이전·이후의 날짜별 장소·시각·설명·조건 등을 비교한 내용이며 모델의 설명과 구분합니다. 변경이 없으면 변경을 확인하지 못했다고 표시합니다. `plan.validation`에 새 검증 결과와 자동 재계획 내역이 있습니다.

오류: INVALID_EDIT_INPUT(400), PLAN_NOT_EDITABLE(409), PLAN_EXPIRED(410), EDIT_SCOPE_VIOLATION/INVALID_AI_RESPONSE(502) 및 기존 Agent 오류입니다. 실패·취소 때 현재 화면과 되돌릴 스냅샷은 유지합니다. 수정 중 자동 재계획 오류로 마지막 검증 초안이 반환되면 남은 문제와 종료 사유를 확인할 수 있습니다.

## 조건과 근거 유지

- 예산, 인원, 취향, 자동차/렌터카/대중교통, 하루 방문 수와 이동 제한을 함께 수정할 수 있습니다. 지역·출발일·기간 변경은 상단 폼에서 새 일정을 생성합니다.
- 수정 스키마 conditionChanges의 null은 유지입니다. 이동 제한 필드의 0은 명시적 제한 해제이며 내부적으로 null로 정규화합니다. 이 경우 긴 이동 점검의 기본 기준(구간 60분·하루 180분)은 유지합니다.
- 장소가 바뀌면 예전 경로는 수정 후 이웃 장소의 좌표와 정확히 일치할 때만 표시합니다. 대중교통으로 바꾸면 기존 자동차 경로를 재활용하지 않습니다.
- 날짜나 조건이 바뀐 뒤 이전 버전의 예산 결과를 그대로 확정 비용으로 표시하지 않습니다. 가격 근거가 없으면 여전히 미확인입니다.
- 영업시간·실내 여부는 모델이 만든 필드를 근거로 채택하지 않습니다. [검증 기준](ITINERARY_VALIDATION.md)을 유지합니다.
- 채팅은 현재 표시된 결과를 수정합니다. 상단 생성 폼은 별도 새 계획 입력이며, 새 생성이 성공하면 채팅과 되돌리기 기록을 초기화합니다.

## 직전 수정 되돌리기

수정이 성공할 때 브라우저 메모리에 수정 전 전체 일정 한 개를 보관합니다. **직전 수정 되돌리기**를 누르면 지도·예산·출처·검증·기존 planId를 함께 복원합니다. LLM이나 외부 API를 호출하지 않습니다. 되돌린 후 다시 채팅하면 복원된 서버 스냅샷을 기준으로 수정합니다.

한 번의 되돌리기를 지원하며 연속 여러 단계 뒤로 가기/다시 실행은 지원하지 않습니다. 수정·생성 중에는 되돌리기를 잠급니다. 실패나 취소는 저장된 되돌리기를 덮어쓰지 않습니다. 새 계획 생성 성공, 기본값 초기화, 페이지 새로고침은 기록을 초기화합니다.

## 임시 보관 범위

서버 메모리에서 버전별 스냅샷을 최대 40개, 발급 후 30분 동안 사용합니다. 만료 항목은 다음 접근 시 정리하고 용량 한도에서는 오래된 항목부터 제거합니다. 서버 재시작 시 세션은 사라집니다. 세션이 없으면 새로 생성하라는 안내를 표시합니다. 되돌린 일정 자체는 브라우저에서 보이더라도 만료된 ID로 추가 수정은 할 수 없습니다.

파일·DB·localStorage에는 저장하지 않습니다. 서버의 도구 기록과 원본 모델 초안은 클라이언트 응답으로 전송하지 않습니다. public/만 공개하는 기존 설정과 `store:false`, 취소·시간·반복·호출 한도, API 키 보호를 유지합니다. 현재 로컬 개발 앱의 임시 세션이며 별도 사용자 계정 저장 기능은 아닙니다.

## 검증

```powershell
npm.cmd run test:edit
npm.cmd test
npm.cmd run check
```

자동 테스트는 날짜 유지·범위 차단·근거 재사용·새 경로 조회·옛 경로/예산 무효화·재검증·세션 만료·변조 입력·HTTP 응답을 검사합니다. Chrome에서 채팅, 수정 내용·이유, 실패·취소, 직전 되돌리기 및 복원 후 수정 기준을 검사했습니다. 모의 도구를 사용하는 검사는 실제 외부 정보를 확인한 것으로 표시하지 않습니다.

실제 OpenAI Responses API로 테스트용 기존 2일 일정과 “둘째 날만 14:00~15:00로 변경” 요청을 전달해 한 번의 요청으로 둘째 날만 수정되고 첫날이 그대로 유지되는 것을 확인했습니다. 추가 도구 호출 없이 종료했고, 날씨·가격·영업시간은 확인 필요 상태를 유지했습니다.
